# Conference Booking API

REST API для управління конференц-залами, бронюваннями і розрахунком вартості оренди.
Тестове завдання, .NET 10 / ASP.NET Core / EF Core.

## Бізнес-задача

Компанія здає конференц-зали в оренду. Клієнту потрібно:

- вести довідник залів (місткість, доступні послуги, базова вартість години);
- шукати зали, вільні на конкретний проміжок часу і потрібної місткості;
- бронювати зал з додатковими послугами і одразу бачити вартість;
- розуміти, звідки взялась сума, а не отримувати одне число.

Вартість оренди залежить від часу доби: ранок і вечір дешевші, обідній пік дорожчий.

## Запуск

```bash
dotnet run --project ConferenceBooking.Api
```

База SQLite створюється автоматично при першому старті, міграція застосовується сама,
початкові дані з ТЗ (зали A/B/C і три послуги) заливаються сідингом.

Swagger: `https://localhost:<port>/swagger` у режимі Development.

Тести:

```bash
dotnet test
```

## Архітектура

```
ConferenceBooking.Api
  Domain/        Hall, Service, Booking - сутності без залежностей
  Pricing/       розрахунок вартості: сітка тарифів і калькулятор
  Application/   бізнес-логіка: ReservationService, ReportService, винятки
  Data/          AppDbContext, конфігурація моделі, сідинг
  Contracts/     DTO запитів і відповідей, мапінг
  Controllers/   тонкий шар HTTP
```

Розподіл простий: контролери не ухвалюють рішень, а прикладний шар нічого не знає
про HTTP. Розрахунок цін винесений в окремий шар, бо це єдина частина із справжньою
складністю, і її треба було покрити тестами незалежно від бази і вебу.

## Технічні рішення

### 1. Ціна рахується посегментно, а не за часом початку

Тарифні смуги в ТЗ **перетинаються**: пікові 12:00-14:00 лежать усередині
стандартних 09:00-18:00. Бронювання з прикладу самого ТЗ (10:00-14:00) проходить
через дві смуги одразу.

Тому інтервал ріжеться по межах смуг, і кожен відрізок множиться на свій коефіцієнт:

```
10:00-12:00  Стандартні  x1.00  ->  4000
12:00-14:00  Пікові      x1.15  ->  4600
                                    ----
                         оренда залу  8600
```

Взяти один тариф за часом початку означало б віддати клієнту робочий код із тихо
неправильними грошима.

Коли смуги накладаються, виграє вужча - для цього у `TariffBand` є `Priority`.
Розрахунок ведеться в хвилинах, тому бронювання з 11:30 або тривалістю 1.5 години
працюють без окремих випадків.

### 2. Знижка застосовується тільки до оренди залу

ТЗ формулює точно: «знижка 20% **на оренду залу**». Тому коефіцієнти смуг множать
лише базову вартість години, а послуги додаються зверху повною сумою.

### 3. Послуга коштує разово за бронювання

ТЗ не вказує одиницю («Проектор: 500 гривень»). Обрано разову оплату,
і це зафіксовано в назві поля - `Service.PricePerBooking`, щоб рішення було видно
з коду, а не лише з документації.

### 4. Ніч 23:00-06:00 - неробочий час

На цей проміжок у ТЗ тарифу немає. Мовчки рахувати його за базовою ставкою було б
вигадуванням, тому такі бронювання відхиляються з поясненням
(`OutsideBusinessHoursException` -> 400).

### 5. Базова вартість - вхідне поле, а не функція місткості

Початкові дані з ТЗ побудовані за сіткою «ціна за особу-годину»:
1500/30 = 50, 2000/50 = 40, 3500/100 = 35. Спокусливо рахувати ціну з місткості,
але ТЗ вимагає приймати базову вартість при створенні залу і змінювати її при
редагуванні - інакше вхідне поле стало б декоративним.

Тому закономірність винесена у **звіт** `/api/reports/seat-prices`: він показує,
який зал вибивається з цінової сітки, і при цьому не ламає контракт API.

### 6. Подвійне бронювання

Перетин інтервалів: `existing.StartsAt < new.EndsAt && new.StartsAt < existing.EndsAt`.
Кінець бронювання виключний, тому 10:00-12:00 і 12:00-14:00 не конфліктують.

Перевірка і вставка виконуються в одній транзакції, інакше два одночасні запити
могли б забронювати той самий зал: обидва перевірили б порожнечу до того, як
хтось із них записав. SQLite серіалізує записувачів, тому повторної перевірки
всередині транзакції достатньо.

На PostgreSQL надійніше перекласти це на базу обмеженням, щоб гонка була неможлива
в принципі:

```sql
ALTER TABLE "Bookings" ADD CONSTRAINT no_overlap
  EXCLUDE USING gist ("HallId" WITH =, tsrange("StartsAt", "EndsAt") WITH &&);
```

Під запит перетинів створено індекс `(HallId, StartsAt, EndsAt)`.

### 7. Видалення залу м'яке

Фізичне видалення знищило б історію бронювань і зламало звіти. Зал помічається
`IsDeleted` і зникає з пошуку. Зв'язок бронювання із залом налаштований на
`DeleteBehavior.Restrict`, щоб випадкове каскадне видалення було неможливим.

### 8. Ціни фіксуються в бронюванні

`Booking` зберігає `HallCost`, `ServicesCost`, `TotalCost` на момент створення.
Зміна тарифу залу не переписує вже виставлені рахунки.

## Безпека

- вхідні дані перевіряються в прикладному шарі (назва, місткість, тривалість,
  існування залу і послуг);
- у бронюванні можна замовити лише послуги, доступні саме в цьому залі;
- усі винятки проходять через один обробник і повертаються як `ProblemDetails`
  з людською причиною, **без стектрейсів**; несподівані помилки лишаються в логах,
  а клієнт отримує загальний текст;
- параметризовані запити через EF Core, рядкової конкатенації SQL немає.

Автентифікація навмисно не додана: у ТЗ немає моделі користувачів і ролей.
У продакшені це JWT з розділенням «клієнт бронює» і «адміністратор редагує зали».

## Звіти

ТЗ просить звіти, «корисні для бізнесу», не називаючи конкретних. Обрані ті,
що відповідають на питання власника:

- **revenue** - скільки заробили за період, скільки з цього зали, скільки послуги,
  середній чек і середня тривалість;
- **utilization** - завантаженість кожного залу у відсотках робочого часу; показує,
  який зал простоює і чи взагалі потрібен;
- **revenue-by-band** - дохід у розрізі тарифних смуг; відповідає на пряме питання,
  чи знижки на ранок і вечір реально приводять клієнтів, чи просто здешевлюють
  ті самі бронювання;
- **service-demand** - як часто замовляють кожну послугу і скільки вона принесла;
- **seat-prices** - вартість особи-години, дає порівняти зали різної місткості
  між собою.

Розклад по смугах не дублюється в базі, а перераховується тим самим калькулятором,
щоб ціна мала одне джерело правди.

## Тести

7 модульних тестів на `PriceCalculator` - там, де ціна помилки найвища:

- бронювання через дві смуги (приклад із ТЗ) розкладається на сегменти;
- вужча смуга перекриває ширшу;
- знижка не поширюється на послуги;
- ранкова знижка;
- дробові години і початок не на рівній годині;
- вихід у неробочий час відхиляється;
- кінець раніше за початок відхиляється.
